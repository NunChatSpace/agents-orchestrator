# Phase 13 — Deployment Plan Backend

## Goal

Implement the backend for creating, deploying, stopping, and deleting deployment plans. A deployment plan selects one worker build per required stack role and runs those as isolated containers, accessible at `http://shiphide.{plan-name}.preview`.

After this phase:
- Deployment plans can be created via API.
- The backend resolves builds (fresh or latest) per role and tracks plan state.
- Deploy execution (container start, nginx config, health check) is stubbed or partially implemented.
- All plan CRUD endpoints are functional.

Nginx config generation and container lifecycle are part of this phase. Health check polling is best-effort in this phase; complete health polling is in phase 15.

CREATE TABLE deployment_plans (

    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),

CREATE INDEX idx_deployment_plans_status  ON deployment_plans(status);

## Service: `backend/internal/services/deployment_plan_service.go`

Interface:

```go
type DeploymentPlanService interface {
    Create(ctx context.Context, userID uuid.UUID, req domains.CreateDeploymentPlanRequest) (*models.DeploymentPlan, []*models.DeploymentPlanRole, error)
    Get(ctx context.Context, id uuid.UUID) (*models.DeploymentPlan, []*models.DeploymentPlanRole, error)
    List(ctx context.Context, userID uuid.UUID) ([]*models.DeploymentPlan, error)
    Stop(ctx context.Context, id uuid.UUID) error
    Delete(ctx context.Context, id uuid.UUID) error
}
```

`Create` logic:

1. Validate `name` matches `^[a-z0-9-]{1,40}$`. Reject duplicates.
2. Validate `stack_id` exists in the stack registry.
3. For each role in the request:
   a. Validate `worker_id` belongs to the correct `worker_group` for that role.
   b. If `build_mode == "latest"`: look up `worker_build_repo.LatestReadyForWorker(workerID)`.
      - If found: assign to role immediately (`build_status=ready`, populate `image_reference`, `image_digest`).
      - If not found: set `build_status=pending`; trigger a fresh build.
   c. If `build_mode == "fresh"`: set `build_status=pending`; trigger a fresh build via `WorkerBuildService.TriggerBuild`.
4. Create `deployment_plan` record with `status=pending`.
5. Create `deployment_plan_roles` records.
6. If all roles have `build_status=ready` immediately: kick off deploy goroutine (advance to `deploying`).
7. Otherwise: plan stays `pending`, waiting for build reports to come in.

**Build report hook**: `WorkerBuildService.ReportBuild` must notify `DeploymentPlanService` when a build completes. One approach: after `ReportBuild` updates the build record, call a `DeploymentPlanService.OnBuildReady(workerBuildID)` method. This method checks if any `pending` plan roles are waiting on that build; if so, updates their `build_status=ready`. If all roles of a plan are now ready, kicks off deploy.

`Stop` logic:

1. Load plan, verify not already stopped.
2. For each role, stop the container: `docker stop {container_name}` + `docker rm {container_name}`.
3. Remove nginx upstream entry for this plan and reload nginx.
4. Update plan `status=stopped`, set `stopped_at`.

`Delete` logic:

1. Plan must be in `stopped` or `failed` state. Reject otherwise.
2. Delete plan and cascade to roles.

## Nginx Config Service: `backend/internal/services/nginx_config_service.go`

Responsibilities:
- Maintain `infra/nginx/preview-upstreams.conf`.
- Write upstream block + server block per running plan.
- Call `docker exec proxy nginx -s reload` after writing.

The backend must know the path to the nginx conf file. Add env var `NGINX_PREVIEW_CONF` defaulting to `/app/infra/nginx/preview-upstreams.conf` (or relative path when running on host). The `proxy` container must mount the same file path.

Generated file format example:

```nginx
# AUTO-GENERATED — do not edit manually
# Managed by DeploymentPlanService

upstream preview_feature_cart {
    server 172.17.0.5:3000;
}

server {
    listen 80;
    server_name shiphide.feature-cart.preview;

    location / {
        proxy_pass http://preview_feature_cart;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

One upstream + server block per running plan. Regenerate the entire file from scratch on each change. Reload nginx after write.

**Docker exec approach**: the backend container must have access to the Docker socket (`/var/run/docker.sock`) to run `docker exec`. Add the socket mount to `docker-compose.yml` for the `backend` service.

## Acceptance Criteria

1. `POST /api/v1/deployment-plans` with valid request returns 201 with plan in `pending` state.
2. Plan name validation rejects names not matching `[a-z0-9-]{1,40}`. Duplicate names return 409.
3. Worker assigned to a role must belong to the role's `worker_group`; mismatch returns 400.
4. `build_mode=latest` with a ready build assigns that build to the role immediately.
5. `build_mode=latest` with no ready build triggers a fresh build and sets role `build_status=pending`.
6. `build_mode=fresh` always triggers a new build.
7. `GET /api/v1/deployment-plans/{id}` returns plan with role states.
8. `POST /api/v1/deployment-plans/{id}/stop` stops the plan; subsequent GET shows `stopped`.
9. `DELETE /api/v1/deployment-plans/{id}` on a non-stopped plan returns 422.
10. `infra/nginx/preview-upstreams.conf` is written with upstream + server block when a plan deploys.
11. Nginx reloads after conf file is written.
